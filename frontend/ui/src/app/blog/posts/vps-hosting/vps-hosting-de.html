Eine Zeit lang war Firebase Hosting meine erste Wahl, um mein Portfolio zu deployen. Es ist schnell eingerichtet, lässt sich gut mit GitHub Actions verbinden, und das kostenlose Kontingent reicht für eine persönliche Website locker aus. Lange schien es die naheliegende Wahl zu sein.

Mit der Zeit habe ich aber die Grenzen von Managed Hosting gespürt. Ich wollte mehr Kontrolle über meine Infrastruktur, mehrere Services auf einem einzigen Server betreiben und ein Setup, das ich von Anfang bis Ende wirklich verstehe. Firebase hat hinter den Kulissen zu viel Magie erledigt, und ich wollte diese Ebene selbst in der Hand haben.

Also bin ich mit allem auf einen VPS bei Hetzner umgezogen. Dieser Artikel erklärt, warum, und zeigt genau, wie ich alles eingerichtet habe.

Warum ich Firebase Hosting verlassen habe

Firebase Hosting ist für seinen Zweck wirklich gut. Statische Dateien, ein globales CDN, automatisches SSL: Es funktioniert sofort, und man muss kaum darüber nachdenken. Wenn du nur eine statische Website brauchst, spricht wenig dagegen.

Ich bin nicht gegangen, weil Firebase schlecht ist, sondern weil ich für die Zukunft etwas anderes wollte. Ein paar Punkte gaben den Ausschlag:

  • Ich wollte mehrere Services unter einem Dach betreiben, ohne mit getrennten Firebase-Projekten zu jonglieren
  • Ich wollte volle Kontrolle über die Serverumgebung, das Netzwerk und den Deployment-Prozess
  • Ich wollte lernen, wie diese Ebene der Infrastruktur wirklich funktioniert
  • Ein VPS ist für meinen Anwendungsfall auf lange Sicht günstiger

Keiner dieser Punkte ist für sich allein ein Ausschlusskriterium, aber zusammen sprachen sie für ein selbst gehostetes Setup. Ich habe mich für Hetzner entschieden, weil es günstig ist, einen guten Ruf hat und die Oberfläche angenehm schnörkellos ist.

Schritt 1: Den Server erstellen

Geh zu Hetzner, öffne ein Projekt und erstelle eine neue Server-Ressource. Wähle einen Standort in der Nähe deiner Besucher, Ubuntu als Betriebssystem und Docker aus den Setup-Optionen. So sparst du dir die manuelle Installation.

Wenn du Docker lieber selbst installieren möchtest, erklärt das Tutorial der Hetzner Community den Ablauf gut.

Schritt 2: Firewall und SSH

Sichere zuerst den Zugang ab. Öffne im Hetzner-Dashboard die Firewall-Regeln des Servers und erlaube diese TCP-Ports:

  • 22: SSH
  • 80: HTTP
  • 443: HTTPS

Einen Benutzer ohne Root-Rechte anlegen

Melde dich über das Terminal im Dashboard als root an und lege sofort einen eigenen Benutzer an. Alles als root auszuführen ist ein Risiko, das du nicht eingehen musst. 

adduser holu
usermod -aG sudo holu
usermod -aG docker holu

Wenn der Benutzer kein Passwort hat, erlaube sudo ohne Passwort, indem du /etc/sudoers mit visudo bearbeitest: 

%sudo   ALL=(ALL:ALL) NOPASSWD: ALL

Wechsle dann mit su - holu zum neuen Benutzer und mach von dort aus weiter.

Anmeldung mit SSH-Schlüssel

Kopiere deinen öffentlichen Schlüssel in die Datei mit den autorisierten Schlüsseln auf dem Server: 

mkdir -p ~/.ssh
nano ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
chmod 700 ~/.ssh

Teste von deinem lokalen Rechner aus, ob die Anmeldung mit dem Schlüssel funktioniert, bevor du weitermachst: 

ssh holu@<SERVER_IP>

Wenn das klappt, deaktiviere die Anmeldung als root und die Passwort-Authentifizierung in /etc/ssh/sshd_config: 

PermitRootLogin no
PasswordAuthentication no
sudo systemctl restart ssh

UFW und Fail2Ban

Installiere UFW und erlaube nur die Ports, die du wirklich brauchst:

sudo apt update && sudo apt install ufw -y
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable

Installiere dann Fail2Ban, damit wiederholte fehlgeschlagene Anmeldeversuche automatisch blockiert werden: 

sudo apt install fail2ban -y
sudo cp /etc/fail2ban/jail.conf /etc/fail2ban/jail.local

Öffne jail.local, suche den Abschnitt [sshd] und stelle sicher, dass er aktiviert ist: 

[sshd]
enabled = true
port    = ssh
filter  = sshd
logpath = /var/log/auth.log
maxretry = 5
sudo systemctl enable fail2ban
sudo systemctl start fail2ban

Schritt 3: Domain und DNS

Dieser Schritt ersetzt, was Firebase Hosting automatisch erledigt hat. Geh zu deinem Domain-Registrar und lege einen A-Record an, der deine Domain auf die IP-Adresse des Servers zeigt. Füge bei Bedarf einen CNAME für www hinzu.

Prüfe die Verbreitung mit:

dig +short yourdomain.com

Schritt 4: Deployment mit Docker und Caddy

Mein Setup nutzt Docker Compose für jeden Service und Caddy als Reverse Proxy. Alle Deployment-Dateien liegen unter /opt/docker/, und jeder Service bekommt ein eigenes Unterverzeichnis. 

/opt/docker/
|–– caddy/
|   |–– compose.yaml
|   |–– Caddyfile
|–– webfolio/
    |–– compose.yaml
    |–– .env
    |–– secrets/
        |–– application-secrets.properties

Warum Caddy statt Nginx?

Caddy kümmert sich automatisch um TLS. Es spricht mit Let's Encrypt, holt Zertifikate und erneuert sie, ganz ohne Cronjobs und ohne manuelle Schritte. Bei Firebase war HTTPS einfach da, und genau diese Einfachheit wollte ich auch beim Selbsthosten behalten. Caddy liefert das.

Ein gemeinsames Docker-Netzwerk namens proxy verbindet alle Services mit Caddy. Du legst es einmal an, und jeder neue Service tritt ihm einfach bei.

Einrichten und deployen

sudo mkdir -p /opt/docker/{caddy,webfolio/secrets}
sudo chown -R $(whoami):docker /opt/docker
chmod 750 /opt/docker /opt/docker/caddy /opt/docker/webfolio /opt/docker/webfolio/secrets

Kopiere deine Deployment-Dateien mit scp von deinem lokalen Rechner, verbinde dich per SSH und trage deine Domain, die Umgebungsvariablen und die Secrets ein. Setze dann die richtigen Berechtigungen: 640 für Konfigurationsdateien und 600 für alles Vertrauliche.

Ein Punkt, auf den du achten solltest: Wenn dein App-Container nicht als root läuft, kann er eine Secrets-Datei nicht lesen, die komplett deinem Host-Benutzer gehört. Prüfe, mit welcher UID der Container läuft: 

docker inspect your-image:latest | grep -i user

Passe dann den Besitzer an, damit der Container die Datei lesen kann:

sudo chown 185:holu /opt/docker/webfolio/secrets/application-secrets.properties
sudo chmod 660 /opt/docker/webfolio/secrets/application-secrets.properties

Lege das gemeinsame Netzwerk an, starte zuerst Caddy und dann die App:

docker network create proxy
cd /opt/docker/caddy && docker compose up -d
cd /opt/docker/webfolio && docker compose up -d

Caddy erkennt die Domain, holt ein Zertifikat, und die Website ist unter https://yourdomain.com erreichbar. Das erste Deployment ist geschafft.

Services aktualisieren und hinzufügen

Eine neue Version auszurollen dauert nur ein paar Befehle:

cd /opt/docker/webfolio
docker compose pull
docker compose up -d

Compose erkennt, dass sich das Image geändert hat, und erstellt nur diesen Container neu. Alles andere läuft weiter. Alte Images räumst du danach so auf: 

docker image prune -f

Eine zweite Website auf demselben Server hinzuzufügen ist genauso einfach. Ein neues Verzeichnis, eine neue compose.yaml, die dem Netzwerk proxy beitritt, ein neuer Block in der Caddyfile, und fertig. Nichts, was schon läuft, wird angefasst, und Caddy stellt das Zertifikat für die neue Domain automatisch aus.

Hat es sich gelohnt?

Für meinen Anwendungsfall auf jeden Fall. Ich habe einen Server, auf dem mehrere Services laufen, sehe genau, wie alles zusammenhängt, und zahle weniger, als ich beim Skalieren auf einer Managed-Plattform zahlen würde.

Trotzdem ist Firebase Hosting in vielen Situationen weiterhin die richtige Wahl. Wenn du einfach nur eine statische Website ohne Aufwand online bringen willst, ist es kaum zu schlagen. Die Migration hat sich für mich nur gelohnt, weil meine Anforderungen über das hinausgewachsen waren, wofür es gemacht ist.

Wenn du über einen ähnlichen Umzug nachdenkst und Fragen zu einem Teil dieses Setups hast, melde dich gern bei mir.
