Een tijdlang was Firebase Hosting mijn vaste keuze om mijn portfolio te deployen. Het is snel opgezet, werkt mooi samen met GitHub Actions en de gratis laag is ruim genoeg voor een persoonlijke site. Lange tijd voelde het als de vanzelfsprekende keuze.

Maar na verloop van tijd begon ik de grenzen van managed hosting te voelen. Ik wilde meer controle over mijn infrastructuur, meerdere services op één server kunnen draaien en een opzet die ik echt van begin tot eind begreep. Firebase deed te veel magie achter de schermen, en ik merkte dat ik die laag zelf in handen wilde hebben.

Daarom heb ik alles verhuisd naar een VPS bij Hetzner. In dit artikel leg ik uit waarom, en laat ik precies zien hoe ik het heb opgezet.

Waarom ik Firebase Hosting heb verlaten

Firebase Hosting is echt goed in waar het voor bedoeld is. Statische bestanden, een wereldwijd CDN, automatische SSL: het werkt direct en je hoeft er nauwelijks over na te denken. Als je alleen een statische site nodig hebt, is er weinig tegenin te brengen.

Ik ben niet vertrokken omdat Firebase slecht is, maar vooral omdat ik andere plannen had voor de toekomst. Een paar dingen gaven de doorslag:

  • Ik wilde meerdere services onder één dak hosten, zonder te jongleren met losse Firebase-projecten
  • Ik wilde volledige controle over de serveromgeving, het netwerk en het deploymentproces
  • Ik wilde leren hoe deze laag van de infrastructuur echt werkt
  • Op de lange termijn is een VPS voor mijn situatie goedkoper

Geen van deze punten is op zichzelf doorslaggevend, maar samen maakten ze duidelijk dat een eigen opzet de juiste stap was. Ik koos Hetzner omdat het betaalbaar is, een goede reputatie heeft en de interface verfrissend nuchter is.

Stap 1: de server aanmaken

Ga naar Hetzner, open een project en maak een nieuwe server aan. Kies een locatie dicht bij je publiek, kies Ubuntu als besturingssysteem en selecteer Docker bij de installatieopties. Dat bespaart je de handmatige installatie.

Wil je Docker liever zelf installeren, dan legt de tutorial van de Hetzner-community het goed uit.

Stap 2: firewall en SSH

Scherm eerst de toegang af. Open in het Hetzner-dashboard de firewallregels van de server en sta deze TCP-poorten toe:

  • 22: SSH
  • 80: HTTP
  • 443: HTTPS

Een gebruiker zonder rootrechten aanmaken

Log via de terminal in het dashboard in als root en maak meteen een eigen gebruiker aan. Alles als root draaien is een risico dat je niet hoeft te nemen. 

adduser holu
usermod -aG sudo holu
usermod -aG docker holu

Heeft de gebruiker geen wachtwoord, sta dan sudo zonder wachtwoord toe door /etc/sudoers te bewerken met visudo: 

%sudo   ALL=(ALL:ALL) NOPASSWD: ALL

Wissel daarna naar de nieuwe gebruiker met su - holu en ga daar verder.

Inloggen met een SSH-sleutel

Kopieer je publieke sleutel naar het bestand met geautoriseerde sleutels op de server: 

mkdir -p ~/.ssh
nano ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
chmod 700 ~/.ssh

Test vanaf je eigen computer of inloggen met de sleutel werkt, voordat je verdergaat: 

ssh holu@<SERVER_IP>

Werkt het, schakel dan het inloggen als root en de wachtwoordauthenticatie uit in /etc/ssh/sshd_config: 

PermitRootLogin no
PasswordAuthentication no
sudo systemctl restart ssh

UFW en Fail2Ban

Installeer UFW en sta alleen de poorten toe die je echt nodig hebt:

sudo apt update && sudo apt install ufw -y
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable

Installeer daarna Fail2Ban, dat herhaalde mislukte inlogpogingen automatisch blokkeert: 

sudo apt install fail2ban -y
sudo cp /etc/fail2ban/jail.conf /etc/fail2ban/jail.local

Open jail.local, zoek de sectie [sshd] en zorg dat die is ingeschakeld: 

[sshd]
enabled = true
port    = ssh
filter  = sshd
logpath = /var/log/auth.log
maxretry = 5
sudo systemctl enable fail2ban
sudo systemctl start fail2ban

Stap 3: domein en DNS

Dit is de stap die vervangt wat Firebase Hosting automatisch regelde. Ga naar je domeinregistrar en maak een A-record aan dat je domein naar het IP-adres van de server laat wijzen. Voeg zo nodig een CNAME voor www toe.

Controleer of de wijziging is doorgevoerd met:

dig +short yourdomain.com

Stap 4: deployment met Docker en Caddy

Mijn opzet gebruikt Docker Compose voor elke service, met Caddy als reverse proxy. Alle deploymentbestanden staan onder /opt/docker/, en elke service krijgt een eigen submap. 

/opt/docker/
|–– caddy/
|   |–– compose.yaml
|   |–– Caddyfile
|–– webfolio/
    |–– compose.yaml
    |–– .env
    |–– secrets/
        |–– application-secrets.properties

Waarom Caddy en niet Nginx?

Caddy regelt TLS automatisch. Het praat met Let's Encrypt, haalt certificaten op en vernieuwt ze, zonder cronjobs en zonder handmatige stappen. Bij Firebase was HTTPS er gewoon, en ik wilde iets dat die eenvoud ook bij self-hosting behield. Caddy doet precies dat.

Een gedeeld Docker-netwerk met de naam proxy verbindt alle services met Caddy. Je maakt het één keer aan, en elke nieuwe service sluit zich er gewoon bij aan.

Opzetten en deployen

sudo mkdir -p /opt/docker/{caddy,webfolio/secrets}
sudo chown -R $(whoami):docker /opt/docker
chmod 750 /opt/docker /opt/docker/caddy /opt/docker/webfolio /opt/docker/webfolio/secrets

Kopieer je deploymentbestanden vanaf je eigen computer met scp, log in via SSH en vul je domein, omgevingsvariabelen en secrets in. Zet daarna de juiste rechten: 640 voor configuratiebestanden en 600 voor alles wat gevoelig is.

Let op één ding: als je app-container als gebruiker zonder rootrechten draait, kan hij een secrets-bestand dat volledig van je hostgebruiker is niet lezen. Controleer met welke UID de container draait: 

docker inspect your-image:latest | grep -i user

Pas daarna de eigenaar aan, zodat de container het bestand kan lezen:

sudo chown 185:holu /opt/docker/webfolio/secrets/application-secrets.properties
sudo chmod 660 /opt/docker/webfolio/secrets/application-secrets.properties

Maak het gedeelde netwerk aan, start eerst Caddy en daarna de app:

docker network create proxy
cd /opt/docker/caddy && docker compose up -d
cd /opt/docker/webfolio && docker compose up -d

Caddy herkent het domein, haalt een certificaat op en de site staat live op https://yourdomain.com. De eerste deployment is klaar.

Services bijwerken en toevoegen

Een nieuwe versie deployen kost twee commando’s:

cd /opt/docker/webfolio
docker compose pull
docker compose up -d

Compose ziet dat de image is veranderd en maakt alleen die container opnieuw aan. Al het andere blijft gewoon draaien. Ruim oude images daarna op met: 

docker image prune -f

Een tweede site aan dezelfde server toevoegen is net zo overzichtelijk. Een nieuwe map, een nieuwe compose.yaml die zich aansluit bij het proxy-netwerk, een nieuw blok in de Caddyfile, en klaar. Je hoeft niets aan te raken wat al draait, en Caddy regelt het certificaat voor het nieuwe domein automatisch.

Was het de moeite waard?

Voor mijn situatie absoluut. Ik heb één server met meerdere services, volledig zicht op hoe alles met elkaar verbonden is, en ik betaal minder dan ik kwijt zou zijn als ik op een managed platform zou opschalen.

Toch blijft Firebase Hosting in veel situaties de juiste keuze. Wil je gewoon zonder gedoe een statische site online hebben, dan is het moeilijk te verslaan. De migratie was voor mij alleen zinvol omdat mijn wensen verder waren gegroeid dan waarvoor het bedoeld is.
